# STAR 交付模板

先核对 [证据规则](evidence-rules.md)，按用户要的格式展开。正文围绕具体问题和本人动作；证据卡保留推导边界。

## 简历要点

`<本人具体动作> <解决的场景/问题>；<有依据的结果及条件>。`

- 一条通常 1–2 行，按目标岗位保留最相关的细节；篇幅服从用户交付要求。
- 具体动词跟随实际责任：“实现 X 中的 Y”“修复 Z 场景”同样可以表达协作贡献。
- 有可信比较记录才写提升数字；没有数字时写可回查的通过条件。
- 责任、结果或披露待确认时，在素材中标“候选”，不混入可直接投递的正文。

```text
候选要点：<场景 + 本人动作 + 能支撑的结果> [E01]
证据附注 E01：<来源与版本>；<验证环境和范围>；<本人贡献确认状态>；<未覆盖>。
待补：<直接影响这句话的一个问题或一份记录>。
```

## 项目档案

```text
项目：<名 / 安全别名>
类型与角色：<工作 / 个人 / fork / 练习 / 研究>；<本人责任及确认依据>
S 背景：<使用场景、问题和约束>
T 任务：<本人实际承担的目标>
A 行动：<改动路径、选择和代价；上游/团队/AI参与>
R 结果：<在什么条件下验证了什么> [E01]

难点：<一句话触发与现象>
- 现象：<输入、状态、时序与结果>
- 定位：<对照或证据；缺同期记录时注明>
- 根因 / 假设：<已确认到哪一步>
- 解法与代价：<具体改变、适用条件>
- 验证：<版本、环境、手段、结果和未覆盖>

反思：<改变过的判断；下一次有判据的验证动作>
```

已有档案保留其上下文，补必要的证据和边界，不为了模板改写全部章节。

## 面试讲述

90 秒围绕“问题 → 本人责任 → 一个取舍 → 一个可回查结果”，证据不足的地方直接说明。

```text
讲述：<一句话定位 + 本人承担的任务 + 一个难点/取舍 + 验证结果与边界>
追问：为什么这样定位？替代方案的代价是什么？如何构造反例？
回答依据：<证据卡或原档案引用>
待补追问：<责任、基线或记录尚未确认的部分；不编出答案>
```

## 通用证据卡

```text
E01 主张：
事实状态：本轮核实 / 历史记录 / 待确认
来源：<仓库/安全别名 + 相对路径或记录链接>
快照与时间：<HEAD/版本 + 工作树状态 + 核查日期>
口径与条件：<计数对象/样本/变量/比较基线>
验证：<静态核查/测试/模拟/浏览器/部署/业务；手段、结果和证据>
本人贡献：<本人改动与依据；团队/上游/AI参与；待确认项>
未覆盖与披露：
```

证据编号用于回查，不是质量评分。同一数字只维护一份口径，其他输出引用该卡。
