# 证据规则

用来源约束一句话能写到哪里。事实正确、本人负责、允许披露是三个需要分别确认的问题。

## 一张证据卡的最小信息

| 字段 | 记录什么 |
| --- | --- |
| 主张与状态 | 一条具体结论；本轮核实 / 历史记录 / 待确认 |
| 项目对应 | 有多名或副本时，记录展示名、用户原称、仓库/路径、同源副本与上游依赖 |
| 来源 | 仓库或安全别名、相对路径、相关提交/记录；行号按需提供 |
| 快照与时间 | HEAD 或固定版本、核查日期；工作树有改动时注明，必要时附所读文件的哈希 |
| 口径与条件 | 样本、计数对象、范围、变量含义、环境和基线 |
| 验证 | 实际采用的手段、命令/报告入口、观察结果；没运行就写静态核查 |
| 本人贡献 | 本人新增/修改与依据；团队、上游、AI 的参与；待本人确认项 |
| 未覆盖与披露 | 当前不能推出的结论，以及允许使用的材料边界 |

同一结论引用多个来源时，指出各自支撑的部分。简历正文可省略长卡，素材交付保留卡或链接。

## 简历选材先找成果

- 先读已有成果段，查 benchmark/perf、QA/验收、原始报告和相关提交中的结果候选；回查原值、改后值、计算式、样本、版本和环境，再选带来结果的关键行动。
- 有原始记录支撑的历史指标可按当时版本和日期引用，注明本轮是否复测；未复跑不等于没有成果。仅有档案转录的数字仍标原始记录待补，不因新版本计数不同就否定旧结果。
- 时间、材料覆盖、请求/写入减少、故障恢复或通过条件都可成为成果。测试总数只说明验证范围，不能替代某次改动的效果；缺少可信数字就写可回查结果，不编数字，也不强迫每条量化。

## 项目名称与归属

- 把用户原称、交付展示名、仓库名/路径、同源副本、上游依赖及基线对应起来。应用与依赖分别记录责任；名称相近、同 remote/HEAD 或本地存在不证明本人原创，副本不重复计项目。
- 用户对名称提出疑问时，先说明对应的是应用、运行时还是副本；指代仍影响选材时只补这一处。名称疑问不自动转为归属否认，明确的归属纠正也不能被更早的笼统确认覆盖。
- 沿用已有明确本人确认的范围；新的明确确认或纠正更新相关候选、地图与证据卡的口径，不反复索取同一确认。技术结果仍查原始证据，外部运行时和上游能力不转嫁为本人原创。

## 材料能支持什么

| 已获得的材料 | 可以支持的结论 | 仍需其他证据的结论 |
| --- | --- | --- |
| 固定版本源码 | 该版本包含某个机制；在明确假设下推导操作次数 | 本人原创、真实运行通过、延迟下降、生产收益 |
| 静态计数 | 指定范围内的文件/定义/调用位置数量 | 实际执行用例数、覆盖率、通过数 |
| CI 配置 | 计划在指定触发条件下执行哪些任务与目标平台 | 某次 CI 已运行且全绿、二进制在所有平台可运行 |
| 运行日志或 CI run | 对应版本与环境下，所列断言和任务的运行结果 | 未执行的用例、跳过平台、部署或业务完成 |
| 测试替身/模拟上游 | 受控条件下的状态、错误、恢复与请求行为 | 真实厂商副作用、生产兼容或外部动作恰好一次 |
| 真实浏览器、本地后端 | 被操作的页面与本地链路在当时条件下的行为 | 未打开的完整产品页、生产代理、真实用户规模 |
| 部署、交易或业务验收记录 | 被记录的环境、版本、样本和业务结果 | 未记录的总体规模、其他环境或长期稳定性 |
| 历史档案/提交说明 | 当时记录过某个改动、数字或解释，可据此找原证据 | 本轮重验通过、独立核实全部内容、无条件因果关系 |
| 本人说明 | 本人自述的角色、责任和参与时间 | 独立技术验证、未提供的量化成绩 |

“实现”“配置了检查”“某次运行通过”“部署成功”“业务完成”分别写清楚，不用一个笼统的“已验证”盖住差异。CI 链接或部署入口应对应具体版本；仅打开网页不证明功能验收。

## 数字的口径

- **测试**：文件数、函数定义数、收集用例数、运行通过数、断言调用位置数是不同对象。参数化、循环、跳过、辅助函数会改变它们的关系。需要执行数时读取 runner 的收集/运行报告；静态结果必须写“静态”。
- **修复覆盖**：项目整体套件规模可以另记；具体修复列实际相关用例及断言，不把套件总数接在单项修复后暗示专属覆盖。
- **代码量**：写明目录、语言、排除规则与版本。代码减少只证明该口径下的代码量变化；可维护性、性能或成本改善需要另证。
- **操作次数公式**：说明变量与拓扑。例如 N 台目标主机共享同一个跳板时，连接池的 N+1 中 1 指共享跳板握手。多跳、重试、其他跳板不能直接套同一公式。
- **性能前后值**：保留旧/新版本、相同样本、资源与配置、测量方法和重复情况。操作数推导写成机制变化；没有实测时间就不转换为延迟提升百分比。
- **业务数据**：记录原始统计口径、时间窗、样本与允许披露范围；来自本人说明时注明。没有依据的用户量、日活、吞吐、收益或使用人数不补写。

## 个人贡献的核对

1. 先读用户已有角色说明，并确定工作项目、个人作品、fork、练习或研究的材料类型。
2. 在已确认职责范围内描述本人具体行动；归属仍不明时补相关 diff、同期记录或本人确认。不从项目总功能扩大已确认的责任，也不把没有来源的旧档案标签当作本人自述。
3. fork 记录上游地址与基线，描述本人实际新增/修改的路径和行为。上游功能只作背景；无法比对基线时将该条贡献保留为待确认。
4. git 作者与仓库所有权用于寻找线索，不能据此推断团队分工、原始作者或 AI 使用范围。AI 辅助写到已知事实，仅在未知部分影响当前主张时补关键缺口。
5. 工作树有未提交修改时，说明读取的是工作树而非纯 HEAD。重复副本不重复计算项目数；相近名称不能把一个项目的测试成绩移给另一个项目。

## 缺证据、旧记录与冲突

- 有历史日志且版本可定位：保留历史结果与日期，注明本轮是否重跑。
- 只有档案中的数字：标“历史档案记述，原始记录待补”，对外短句优先用已支撑的机制或验收事实。
- 当前源码计数与旧档案不同：检查版本、目录与计数口径，不判定旧结果必然错误，也不直接改成新计数。
- 定位不到源码：保留项目与问题线索，列出需要的最小材料；不拿同名 fork 或相近仓库替代。
- 只有解法没有当时诊断记录：写目前可解释的机制或假设，不补出一段虚构的排障经过。

证据不足时仍可交付候选素材与少量待补项。技术结论已核实但责任或披露尚未确认的句子，保留候选标记。
