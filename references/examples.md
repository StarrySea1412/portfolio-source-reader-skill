# 示例：证据怎样约束表述

这些示例用于学习采集深度与表述边界。第一个有实际源码核查；后两个是明确标注的假设输入，不是真实履历或成绩。采用任何候选句前，仍需确认用户本人贡献及披露范围。

## 1. 源码核实：同一跳板的连接复用

**来源**：GitHub 上的 `hermes-watch@8a9c01070b172cb6cb2d3dd1d6cca26fa692005d`，`backend/app/ssh.py`（blob `25a4887c68bfc3d83610343a7d11e0942b358ecc`）；2026-11-24 通过 API 读取固定版本源码，未运行项目。

- `ssh.py:100` 描述“同跳板的 N 台主机共享一次握手”；缓存按跳板配置键建立，目标主机另建隧道连接。
- **N 指共享同一跳板配置键的目标主机数**，1 指共享跳板连接的握手。在跳板仅建立一次、连接保持存活且 N 个目标各握手一次的复用路径下，可以比较逐主机两层连接的 2N 与 N+1。
- 这是有前提的操作次数推导。本次没有运行巡检、测试或延迟基准；冷启动并发、重建、重试及多个跳板的成本需另核，不能声称任意一轮都恰好 N+1。
- 文件和仓库的存在不证明用户实现了该机制；相关提交差异及本人责任仍需确认。

**候选素材（责任确认后再采用）**：

```text
S：多台目标主机共用一个跳板，重复建立跳板连接。
T：<本人承担的采集/连接改动，待确认>
A：<本人具体改动，待查相关 diff>；源码按跳板配置键复用连接。
R：共享同一配置键且跳板成功复用的路径下，N 个目标连接加一次跳板连接可推导为 N+1；未测延迟收益。
```

代码回查：[固定版本 ssh.py](https://github.com/StarrySea1412/hermes-watch/blob/8a9c01070b172cb6cb2d3dd1d6cca26fa692005d/backend/app/ssh.py#L100)。本轮 API 已读到对应版本；浏览器显示、匿名访问和运行验收未在这次源码核查中执行。

## 2. 只有历史档案：身份服务的并发轮换

**假设输入**：档案记述“并发刷新用了行锁”“项目有 284 个测试函数”，但对应源码和测试报告暂不可访问。

**处理**：

- 保留行锁方案为“历史档案记述，原始实现待回查”。定位、根因、本人责任没有原记录的部分不能补齐成故事。
- 284 是档案记述的项目函数数，不能接在这次修复后写成专属覆盖，也不能写成本轮测试通过数。
- “99% 的正常请求”“消除线上故障”等主张没有统计或运行依据时，不进入候选成果。
- 最小补证：相关提交/源码片段、并发用例的断言与报告、本人承担的改动；不要求用户重新填所有项目。

**可交付**：一段带历史与待确认标记的方案素材，加上述补证项；现阶段不输出“独立重构并经 284 项测试证明”的定稿句。

## 3. fork：功能存在与本人修改

**假设输入**：用户给出一个 fork，README 已有审批、回滚与长期记忆；本轮只能看到某个超时恢复路径的修改。

**处理**：

- 记录上游地址与可比基线，查看与本次问题相关的差异。
- 背景可以介绍整体产品；行动只描述已有依据的本人修改，其他功能保留为上游或归属待核。
- 有模拟上游的恢复测试，就写模拟条件下验证了恢复；真实厂商副作用、完整产品验收和生产成绩另行补证。
- 用户自述、diff 核查和 AI 辅助分别注明。没有确认责任时，产出候选素材而不是补写“独立完成整个产品”。
