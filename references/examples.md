# 示例

以下项目、数字和记录均为合成材料，用于示范如何择取证据和组织措辞。

## 1. 统一登录与 AI 应用并存

目标岗位偏 Python 后端，用户原简历只列了 AI 文档项目。用户确认自己独立负责统一登录 API，但没有提供正式岗位和任职区间。项目有代码与演练日期，依赖和实现印证 Django REST Framework、PostgreSQL 和 OpenID Connect。已有 PostgreSQL 并发用例的报告，另有合成审计库的查询基准。

简历将统一登录放在商业项目靠前的位置，AI 项目继续保留。技术栈用全名和标准缩写。原简历已经确认的任职照录，缺失的公司、正式岗位和任职年月列为待补项。

> **统一登录服务 · 后端独立开发**
>
> 为内部业务应用提供统一登录与会话管理，使用 Django REST Framework（DRF）、PostgreSQL 与 OpenID Connect（OIDC）。
>
> 将令牌轮换放入事务并加行级锁。PostgreSQL 回归中，6 个并发请求刷新同一令牌时，仅 1 次签发，其余 5 次进入重放处理。
>
> 为审计日期查询增加复合索引。隔离 SQLite 基准使用同一组 20 万条合成记录，30 天趋势重算从 8.0 秒降到 3.2 秒（下降 60%）。

两组证据分别支撑并发正确性与查询耗时。生产数据库表现仍需生产或同条件基准。

## 2. 支付回归与真实验收

项目套件报告为 80 项通过，相关并发用例断言两个相同请求只生成一张订单。另有一笔受控真实付款，渠道查询与网关订单一致。业务系统的权益发放和对账回执未提供。

> 使用数据库唯一约束保护重复下单，PostgreSQL 并发回归中，两次相同请求只生成 1 张订单。用 1 笔真实小额订单核对渠道查询与网关状态。

套件的 80 项可作为测试范围单记，权益到账与对账完成分别需要接入方账本和对账记录。

## 3. 编辑器重构与上游归属

二开项目的档案声称「全模块缩减 80%」。Git 差异只能核实两个指定版本的同一主文件为 5,000 行和 2,000 行。上游已有通用编辑器，本人确认负责状态抽离和导出入口。在隔离 Chrome 中用模拟接口验证过双击，项目只有 CI 配置。

> 在既有编辑器上抽离状态管理和导出操作，主组件从 5,000 行降到 2,000 行（减少 60%）。隔离 Chrome 接模拟 API，双击导出只发 1 次写请求。

代码量结论限定到主组件，浏览器结果保留模拟条件。CI 的可确认状态是已配置检查，实际通过需运行记录。
